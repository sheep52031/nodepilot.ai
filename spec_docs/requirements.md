# NodePilot V6 MVP 需求文件

## 簡介

NodePilot V6 MVP 是基於 **WXT Framework + React + TypeScript** 的現代化 Chrome 擴充插件，專注驗證「標註式學習」的核心價值假設。採用 Chatbot 風格介面，讓使用者主動標記困惑點，AI 生成個人化教學內容。

目標使用者為需要深度理解技術文章的開發者、研究員，他們在閱讀過程中會遇到知識缺口，需要個人化的教學輔助來理解複雜概念。

## 技術架構需求

### 前端技術棧
- **WXT Framework**: 跨瀏覽器擴充插件開發框架
- **React 18**: 現代化 UI 元件開發
- **TypeScript**: 類型安全的開發體驗
- **Tailwind CSS**: 快速 UI 樣式開發
- **Vite**: 快速建置和 HMR 支援

### 擴充插件架構
- **Content Script**: 注入文字選取和標註功能到網頁
- **Background Script**: 處理 API 通信和狀態管理
- **Popup Panel**: Chatbot 風格的 AI 教學介面
- **Manifest V3**: 支援最新的擴充插件規範

### 微服務架構需求
- **主後端服務 (NodePilot Backend)**: FastAPI + uv 套件管理，處理擴充插件業務邏輯
- **語音推理微服務 (Voxtral Service)**: 獨立 Docker 容器，專職處理音頻推理
- **微服務通信**: HTTP API 調用，支援服務間的鬆耦合架構
- **開發靈活性**: Linux RTX 3080 作為推理伺服器，MacBook Air 可遠端開發

### 語音推理微服務架構 (新增)
- **Voxtral Mini 3B Q4 量化模型**: ONNX 社群版本，GPU 加速推理
- **Docker 容器部署**: 完全隔離的推理環境，支援 NVIDIA GPU
- **REST API 接口**: 提供語音轉錄、總結、描述、問答等功能
- **本地模型評估**: 測試 Q4 量化後的性能，為高通筆電部署做準備
- **未來 QNN 轉換**: Q4 ONNX → QNN 格式，適配高通 NPU

### 核心 Agent 系統架構 (更新)
- **語音處理 Agent**: Voxtral Mini 3B Q4 微服務 → OpenAI Whisper API 備援
- **任務規劃 Agent**: GPT-4o / Claude 3.5 Sonnet（開發階段用 API）→ o1-preview 思維模型備援
- **文章上下文分析 Agent**: 智能段落提取 + 文章結構樹狀分析（無需 RAG）
- **筆記檢索 Agent**: Obsidian 筆記 RAG 系統（OpenAI text-embedding-3-large / Voyage AI）
- **教學內容生成 Agent**: Claude 4.0 Sonnet / GPT-5 → 支援 Artifacts 可視化輸出畫布
- **微服務整合**: 主後端透過 HTTP 調用 Voxtral 推理服務

## MVP 核心價值假設
1. **標註式學習比即時問答更有效** - 主動標記困惑點 vs 被動問答
2. **個人化困惑描述提升 AI 教學品質** - 用使用者自己的話描述困惑
3. **批次整合教學比單點解釋更有效** - 將多個困惑點整合成結構化教學

MVP 核心特色：
- 文章載入與顯示
- 文字標註與困惑描述
- AI 個人化教學生成
- 簡單學習狀態追蹤

## MVP 需求

### 需求 1：頁面內容感知與標註

**使用者故事：** 作為一個閱讀 manus.im 技術文章的使用者，我希望 Chrome 擴充插件能自動感知當前頁面內容，並提供文字選取標註功能。

#### 驗收標準

1. 當使用者在 manus.im/blog/* 頁面時，Content Script 應該自動注入標註功能
2. 當使用者選取文字時，系統應該即時顯示標註按鈕並記錄選取範圍
3. 當使用者點擊標註按鈕時，應該彈出困惑描述輸入框
4. 當標註完成時，系統應該將選取文字、困惑描述和頁面上下文傳送給 Background Script
5. 當標註成功後，選取的文字應該高亮顯示並可重複查看

### 需求 2：文字標註與困惑記錄（含音檔功能）

**使用者故事：** 作為一個閱讀技術文章的使用者，我希望能夠標註不理解的文字段落，並透過音檔或文字描述我的困惑，**系統立即處理音檔轉錄並儲存為標註**，讓我能在 Side Panel 中累積多個困惑點，然後自行決定何時生成個人化教學。

#### 工作流程設計

**階段一：標註困惑（立即處理）**
1. 使用者選取文字 → 彈出標註窗口
2. 使用者點擊「標註困惑」→ **立即觸發後端處理**：
   - 若有音檔：優先調用 Voxtral Mini 3B Q4 微服務進行語音轉錄
   - Whisper API 備案：若 Voxtral 服務不可用時的備用方案
   - 立即儲存標註到資料庫
3. 標註成功後顯示在 Side Panel 困惑列表中

**階段二：生成教學（用戶主控）**
1. 使用者在 Side Panel 查看累積的困惑點
2. 使用者自行決定何時點擊「生成教學」
3. 系統整合所有困惑點生成個人化教學

#### 驗收標準

1. 當使用者框選文字時，系統應該記錄選取的文字內容和位置
2. 當使用者完成文字選取時，系統應該顯示標註輸入框
3. **音檔即時處理**：使用者錄製音檔後，點擊「標註困惑」立即觸發 Voxtral Q4 微服務轉錄
4. **認知記錄即時生成**：Voxtral 將音檔轉錄內容立即轉換為用戶認知描述（包含錯誤理解）
5. **立即儲存標註**：標註完成時，系統立即透過 `POST /annotations` 存儲，包含 `{article_id, selected_text, confusion_note, audio_transcription, cognitive_note}`
6. **Side Panel 顯示**：標註儲存成功後，立即在 Side Panel 困惑列表中顯示
7. **文字高亮**：已標註的文字在原文中高亮顯示
8. **累積模式**：使用者可以標註多個困惑點，累積在 Side Panel 中
9. **用戶主控教學生成**：使用者自行決定何時點擊「生成教學」整合所有困惑點
10. **備案方案**：若 Voxtral mini 3B 可在本地運行，直接理解音檔轉為帶有 Function Calling 語意的行為文字

#### 技術實作需求
- **微服務音檔處理**：點擊「標註困惑」立即調用 Voxtral Q4 推理微服務
- **Docker 容器隔離**：Voxtral 推理服務在獨立容器中運行，避免主程式耦合
- **HTTP API 通信**：主後端透過 REST API 調用 Voxtral 服務進行音檔轉錄  
- **服務可用性檢查**：支援 Voxtral 服務不可用時的 Whisper API 備援機制
- **即時 AI 認知轉換**：立即將用戶描述轉為認知記錄格式
- **Side Panel 實時更新**：標註成功後立即更新困惑列表

### 需求 3：多 Agent 智慧上下文整理與教學生成

**使用者故事：** 作為一個累積了多個困惑點的使用者，我希望後端的多 Agent 系統能智慧分析我的音訊困惑和文章上下文，自動規劃最佳的教學生成策略，並整合多種資訊來源生成高品質的個人化教學內容。

#### 多 Agent 協作流程設計

**階段一：即時任務規劃**
1. 用戶標註困惑時立即觸發任務規劃 Agent (GPT-4o/Claude 3.5)
2. 生成結構化 Todo List：筆記檢索、上下文分析、教學生成（去除網路搜尋）
3. 評估任務優先級和執行順序，支援並行執行

**階段二：並行 Agent 執行**
1. 文章上下文分析 Agent：智能段落提取、概念關係、文章結構樹狀分析
2. 筆記檢索 Agent：RAG 向量搜尋 Obsidian 筆記庫相關知識
3. 音訊語意分析：將語音轉錄結構化為概念/疑問/情緒/意圖

**階段三：Artifacts 可視化教學整合**
1. 教學內容生成 Agent (Claude 4.0/GPT-5) 整合所有 Agent 結果
2. 支援 Artifacts 輸出畫布：HTML 可視化教學、互動式範例、圖表生成
3. 個人化教學風格適應 + 多層次驗證

#### 工作流程設計

**困惑管理階段：**
1. 使用者標註困惑後，立即顯示在 Side Panel 困惑列表
2. 使用者可以查看、編輯或刪除個別困惑點
3. 困惑列表顯示選取文字、困惑描述、音檔轉錄結果

**教學生成階段：**
1. 使用者檢視累積的困惑點，自行決定生成時機
2. 使用者點擊「生成教學」主動觸發 AI 教學
3. 系統整合所有困惑點 + 文章上下文生成教學

#### 驗收標準

1. **困惑列表管理**：Side Panel 應該顯示當前文章的所有困惑標註
2. **即時更新**：新增標註後，Side Panel 困惑列表立即更新
3. **困惑點詳情**：每個困惑點顯示選取文字、困惑描述、音檔轉錄（如有）
4. **用戶主控**：使用者自行決定何時點擊「生成教學」按鈕
5. **整合式教學**：AI 根據所有困惑點 + 文章上下文生成整合性教學
6. **Chatbot 介面**：教學內容在 Side Panel 的 Chatbot 風格介面中顯示
7. **Markdown 支援**：支援 Markdown 渲染和程式碼高亮
8. **對話記錄**：保留完整的困惑-教學對話記錄
9. **Context 整合**：將多個困惑點作為重要 Context 餵給 LLM

### 需求 4：基礎學習狀態管理

**使用者故事：** 作為一個學習的使用者，我希望能夠標記自己對概念的理解程度，追蹤學習進度。

#### 驗收標準

1. 當標註建立時，系統應該將狀態初始設為 `unknown`
2. 當生成教學內容後，使用者應該能將狀態標記為 `learning`
3. 當使用者認為已理解時，應該能將狀態標記為 `understood`
4. 當檢視標註列表時，應該能看到每個標註的學習狀態
5. 當統計學習進度時，應該顯示各狀態的標註數量

### 需求 5：純文本閱讀器（Reader）

**使用者故事：** 作為一個閱讀技術文章的使用者，我希望能將網頁文章直接擷取到一個無廣告干擾的暗黑模式閱讀器中，提供更佳的閱讀體驗，同時保留文字標註和 AI 教學功能。

#### 核心價值

參考 Readwise Reader 的「Open in Reader」功能，提供：
- **無廣告干擾**: 移除網頁廣告、導航欄、側邊欄等干擾元素
- **護眼閱讀**: 暗黑模式和可調整字體大小的純文本閱讀體驗
- **完整內容**: 保留文章文字和圖片，確保閱讀完整性
- **標註整合**: 在 Reader 中繼續支援文字標註和 AI 教學生成

#### 驗收標準

1. **內容擷取功能**：
   - Content Script 應該能擷取網頁的完整文章內容（文字+圖片）
   - 自動識別文章主體內容，過濾廣告和非相關元素
   - 保留文章的基本格式結構（段落、標題、列表等）
   - 圖片 URL 應該正確轉換為可顯示的絕對路徑

2. **Reader 頁面功能**：
   - 點擊「Open in Reader」按鈕應該開啟新 Tab 頁面顯示純文本內容
   - Reader 頁面支援暗黑模式和淺色模式切換
   - 文章內容應該採用適合閱讀的字體和排版
   - 保留原文的圖片顯示和基本格式

3. **標註功能整合**：
   - 在 Reader 中應該支援文字選取和標註功能
   - 標註的螢光筆效果應該正常顯示
   - AI 教學生成功能應該在 Reader 中正常運作
   - 標註資料應該與原網頁的標註資料統一管理

4. **使用體驗**：
   - Reader 頁面載入時間應該 ≤ 3 秒
   - 內容擷取準確率應該 ≥ 90%（包含主要文字和圖片）
   - 支援鍵盤快捷鍵（如 ESC 返回、Ctrl+D 暗黑模式切換）
   - 提供閱讀進度指示器

#### 技術實作需求

- **WXT Tab 頁面**: 使用 `browser.tabs.create()` 開啟獨立的 Reader 頁面
- **內容清理算法**: 智慧識別文章主體，移除廣告和導航元素
- **響應式設計**: 支援不同螢幕尺寸的最佳閱讀體驗
- **圖片處理**: 處理相對路徑轉換和圖片載入優化
